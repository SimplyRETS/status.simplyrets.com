## Checks and schedules

| Component               | Public GET URL                    | Expected response    |
| ----------------------- | --------------------------------- | -------------------- |
| API (`api-health`)      | https://api.simplyrets.com/health | HTTP 200; empty body |
| Website (`site-health`) | https://simplyrets.com/health     | HTTP 200; empty body |

The `/health` routes are defined in `retsd/src/Retsd/Handler.hs` and
`simplyretsweb/src/Web/Route.hs` in the platform repository. Both returned 200
without redirects or credentials during implementation (2026-10-08). The API
nginx configuration explicitly disables caching for `/health`. No body assertion
or guessed latency threshold is configured: retries/timeouts/degradation detection
use upstream defaults. These checks test application reachability, not database,
listing freshness, or front-end rendering. That reachability-only scope is
intentional for initial monitoring. No application changes or deeper checks are
part of this replacement.

The workflows use `upptime/uptime-monitor@v1.44.1` with upstream commands and
default UTC schedules:

| Workflow         | Command         | Schedule                       | Activation variable          |
| ---------------- | --------------- | ------------------------------ | ---------------------------- |
| Uptime CI        | `update`        | Every 5 minutes                | `UPPTIME_MONITORING_ENABLED` |
| Response Time CI | `response-time` | Daily, 23:00                   | `UPPTIME_MONITORING_ENABLED` |
| Summary CI       | `readme`        | Daily, 00:00                   | `UPPTIME_MONITORING_ENABLED` |
| Graphs CI        | `graphs`        | Daily, 00:00                   | `UPPTIME_MONITORING_ENABLED` |
| Static Site CI   | `site`          | Daily, 01:00; branding changes | `UPPTIME_PUBLISH_ENABLED`    |

GitHub can delay scheduled runs. Response Time CI **also opens and closes
incidents**; it is not a harmless measurement-only workflow.

## Safety boundaries

Every job requires `refs/heads/master` and its repository variable to equal the
literal string `true`. Missing variables, `false`, implementation branches, and
manual dispatches on other branches all skip the jobs. No setup workflow runs on
configuration pushes. Pushing or merging this implementation alone cannot run
checks, modify Issues, commit monitoring data, or publish the page.

Setup CI, Update Template CI, and Updates CI are intentionally **not installed**.
Upstream Setup CI checks endpoints, regenerates workflows, and publishes the page;
template regeneration would discard our guards and permissions. Upgrade manually
by reviewing upstream changes and retaining these protections. Do not run the
platform repository's old `make statuspage` target: it invokes the legacy
generator and could overwrite the published site.

## Authentication

No App credentials or PAT secrets are configured. All actions use the built-in,
repository-scoped `GITHUB_TOKEN`. `GH_PAT` in action environment blocks is just
Upptime's input name; its value is `${{ github.token }}`, **not** a PAT.

Workflow-level permissions are empty; each job grants only what it uses:

| Jobs                  | Permissions                  | Purpose                                                                                       |
| --------------------- | ---------------------------- | --------------------------------------------------------------------------------------------- |
| Uptime, response time | Contents write; Issues write | Commit/push logs and summaries; create, comment, lock/unlock, and close incidents/maintenance |
| Summary               | Contents write; Issues read  | Commit summary; read repository data (issue deletion is disabled)                             |
| Graphs                | Contents write               | Commit generated graphs                                                                       |
| Site                  | Contents write; Pages write  | Push generated output to `gh-pages`; verify Pages configuration and request a build           |

`GITHUB_TOKEN` pushes do not trigger subsequent push workflows or Pages builds.
The independent schedules/manual runs avoid a push-trigger chain. Static Site CI
explicitly calls the Pages build API after pushing: a successful branch push
alone is **not** proof of website publication. The job first requires existing
Pages settings to be branch deployment from `gh-pages` `/` with the existing
custom domain; it does not change those settings.

The built-in token also supports explicit `workflow_dispatch` calls with Actions
write permission. None of the installed jobs dispatch another workflow, so they
do not request that permission. Automatic template regeneration is outside this
token-only setup: pushing changes to `.github/workflows/` requires a token with
Workflows write permission, which `GITHUB_TOKEN` cannot be granted. If that is
ever deliberately added, use a repository-scoped GitHub App installation token
or fine-grained PAT with Contents and Workflows write; add Actions write only for
cross-workflow dispatch, Issues write for monitoring, and Pages write for explicit
Pages build requests. Do not introduce such a credential for normal operations.

Repository/organization rules may deny bot pushes or write-token permissions.
Verify them during cutover; do not bypass branch protection or add a broad PAT.
Authenticated pushes, incident mutation, and Pages builds cannot be integration
tested locally without deployment credentials. Check them in the first approved
GitHub runs.

## Incident management

Upptime opens issues labeled `status` plus `api-health` or `site-health` for
detected down or degraded endpoints and locks them against outside comments. Team members add
updates as comments. Recovery adds a resolution comment and closes the issue.
Short incidents are retained (`skipDeleteIssues: true`).

For manual incidents, use the **Manual Incident** issue template (labels `status`
and `manual`), or simply open an issue with `status`. Optional component labels
are `component:api` and `component:site`; they are distinct from automation slugs.
Post the initial report and updates as comments, then close the issue manually.
The issue feed is independent of monitoring and site rebuilds, so this still
works when both activation flags are `false` after the Upptime page is deployed.
Stock pages fetch Issues/comments when viewed and cache them in the browser for
two minutes; an already-open page does not continuously refresh.

**Reserve `api-health` and `site-health` exclusively for automated incidents.**
The monitor searches for `status` plus its endpoint slug; a standalone manual
issue lacks that slug and cannot be matched by health-check recovery. `manual`
is an organizational label, not a special exclusion understood by the monitor:
adding a reserved endpoint label would opt the issue into automatic handling.

**Presentation limits (stock Upptime):** active manual incidents appear above
Live Status even when both automated endpoint cards are green. They suppress the
top “All systems operational” banner while open, but do not override measured
cards, uptime percentages, or graphs. A 200 reachability result does not disprove
customer impact. Incident coloring uses lowercase `degraded` in the title rather
than severity labels; other active incidents use the down style. `investigating`
or component/severity labels have no special display behavior. Stock incident
details render comments, not the issue body; put customer-facing reports in
comments. Closed issues move to Past Incidents. No compatibility mapping, custom
presentation code, or historical label migration is provided.

Use `maintenance` and the maintenance issue template for scheduled work. Replace
the ISO timestamps and use `api-health`/`site-health` in `expectedDown` or
`expectedDegraded` as appropriate. The running monitor suppresses matching incidents during that window
and closes completed maintenance issues. It is not a replacement for disabling
monitoring before deployment.

## Controlled cutover (manual GitHub UI)

Nothing in this checklist has been executed by the local implementation.

1. **Review scope and preserve rollback.** Confirm the two health checks and their
   HTTP 200 expectation. Record the current `gh-pages` commit and Pages settings;
   download its files or preserve a backup ref. Keep DNS and `status.simplyrets.com`
   unchanged. Record the previous default branch (`gh-pages`).
2. **Push/review the implementation branch; merge it into `master`, not
   `gh-pages`.** Keep both activation variables absent or `false` in Settings →
   Secrets and variables → Actions → Variables. In Settings → General → Default
   branch, change the default to `master` after review. Neither merging nor the
   default-branch change enables jobs.
3. **Check Actions and Pages settings.** Settings → Actions → General must allow
   GitHub actions, `upptime/uptime-monitor`, and `peaceiris/actions-gh-pages`.
   Explicit job permissions supply the token grants; there is no need to change
   the repository default to blanket read/write or enable PR creation. Check
   applicable branch rules allow these approved bot data/output commits.
   Settings → Pages: Source = **Deploy from a branch**, branch = **gh-pages**,
   folder = **/(root)**; keep custom domain **status.simplyrets.com** and HTTPS.
   Do not select the separate GitHub Actions Pages deployment mode.
4. **Prepare Upptime labels.** Issues → Labels → New label: `status`, `api-health`,
   `site-health`, `maintenance`, `manual`, `component:api`, and `component:site`
   if absent. Keep reserved automation labels off manual issues. Leave the old
   `API`, `Website`, and severity labels alone; no existing Issue needs editing
   or relabeling. This can be done entirely in the UI; local `gh` is not required.
5. **Start monitoring deliberately.** In Actions, open each of the five workflows
   → `…` → Disable workflow before setting flags, so schedules cannot race the
   initial sequence. Settings → Secrets and variables → Actions → Variables →
   New repository variable: `UPPTIME_MONITORING_ENABLED` = `true`. Leave
   `UPPTIME_PUBLISH_ENABLED` absent/`false`. In Actions enable Response Time CI →
   Run workflow → select **master**. This first run can create real incidents if
   a check fails: proceed only once approved. Inspect logs, `history/api-health.yml`,
   `history/site-health.yml`, `history/summary.json`, and any new Issues. Confirm the
   responses, pushes, and summaries succeeded; Upptime can log some API failures
   without failing the overall run. Enable/run Uptime CI on **master** next.
6. **Initialize presentation data.** Enable and manually run Summary CI, then
   Graphs CI on **master**, waiting for each to finish. Confirm only `master`
   changed and both endpoints have data. Initial uptime percentages describe
   checks since activation, not the legacy incidents.
7. **Approve publication.** Set repository variable `UPPTIME_PUBLISH_ENABLED` =
   `true`; enable Static Site CI and Run workflow on **master**. Enabling it also
   permits its daily schedule and branding-change trigger. Confirm the output
   commit on `gh-pages` contains `CNAME`, logo/favicon, `.nojekyll`, and generated
   site files, not the old template/styles or source workflows. Then inspect the
   Pages build/deployment run and visit https://status.simplyrets.com, including
   history/incident routes. A rejected build API request must be investigated;
   do not assume the branch push published successfully or silently add a PAT.
8. **Leave standard schedules enabled.** Keep template updates absent. Confirm
   subsequent scheduled checks and response-time samples commit successfully.
   Verify creation/recovery on a real incident or in a separate sandbox; do not
   simulate failure by changing a production URL.

Before creating a test manual incident in production, test it in a separate
sandbox or wait for a real customer-impact report. Confirm that an open
`status`/`manual` issue appears above green checks, updates show as comments, and
closing it moves it to Past Incidents. Keep reserved automation labels off it.

**Stop/rollback:** set both variables to `false`, disable the five workflows, and
cancel any already-running/queued runs (flags do not stop jobs already started).
Republish the saved legacy output only after explicit rollback approval. A human
push to the Pages branch can trigger its build; a token-driven restore also needs
an explicit Pages build. Restore the previous default branch if desired. Do not
delete new Issues or reset shared history. DNS need not change.
